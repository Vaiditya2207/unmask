## 1. Incidents: did the published package differ from git?

**Pattern [E, across rows]:** in 9 of the 10 incidents, the key malicious change was **visible only in the published package**. A source-vs-package diff would have shown an unexplained file, install script or dependency. Detection times range from minutes (scanner companies watching the registry) to weeks (xz).

**Exception:** keyv@6.0.0 is the honest counterexample, because there the attacker compromised the source itself [E20].

## 2. Personas: who does this check today

| Persona                                                                         | What triggers the check and how often                                                                                                                                                                                    | What evidence they need to act                                              | How many false alarms they tolerate                                                                                                                          |
| ------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Distro packager (Debian)                                                        | Each new upstream release. One Debian developer describes routinely diffing `git archive $TAG` against the downloaded tarball [E21]. Debian's `dgit`/tag2upload tooling checks that the source tarball matches git [E21] | File-level diff against the signed tag                                      | Low. They read diffs by hand, and generated autotools files are a known source of noise [E21] **[H]**                                                        |
| Maintainer, right after a release                                               | Every release, ideally automatically. nx caught its compromise only because provenance was missing [E12]. StepSecurity sells a product that ties each release to a CI run [E22]                                          | The CI run that built it, the commit SHA, the provenance link               | Very low. The useful answer is "was this release mine?" **[H]**                                                                                              |
| Registry and security-research companies (Aikido, Socket, Datadog, Microsoft)   | Every new version on the registry. Aikido claims a median detection time of 5 minutes [E14]                                                                                                                              | Behaviour first: install scripts, network calls, obfuscated code [E14][E23] | Medium. Humans review what the automation flags [E14]                                                                                                        |
| Company security team reviewing a dependency bump (for example a Dependabot PR) | Per pull request. Mostly relies on vulnerability databases. Snyk matches packages "on ecosystem, name, and version" and does not consider provenance [E24]                                                               | One clear verdict per PR, with a link they can read                         | **Very low.** False positives are the top detection pain in the 2025 SANS survey (73%, vendor-reported) [E25]. I could not find SCA-specific numbers **[H]** |

**[H]** The most underserved persona is the security engineer reviewing a dependency-bump PR. Today they get "no known CVE" or a behaviour alert. Nothing tells them "this version's package matches its tagged source except for these explained build outputs."

## 3. Differentiation: what each tool does and does not do

| Tool                                        | What it does                                                                                                                                                                                   | What it does _not_ do (for "diff the package against its source and explain")                                                                                                                                                                            |
| ------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **npm provenance** / `npm audit signatures` | Signed link from a package to its repository, commit and build workflow, checked via Sigstore [E26][E27]                                                                                       | npm's docs say provenance "does not guarantee the package has no malicious code" [E26]. It does not compare contents. Packages without provenance still install [E12]. Legitimate workflows can produce valid provenance for malicious builds [E19][E20] |
| **PyPI PEP 740 attestations**               | Tie each distribution's digest to the identity of its Trusted Publisher [E28]                                                                                                                  | The docs make no claim that the distribution matches its source or is safe [E28]                                                                                                                                                                         |
| **OSS Rebuild (Google)**                    | Rebuilds popular npm, PyPI and crates packages, "semantically compare[s]" them with normalization, and refuses to attest packages containing code that was never submitted to the source [E29] | Covers only "the most popular packages" [E30]. Its result is attest or don't. Its public docs do not describe a per-file explanation of differences [E30] **[H on the output]**                                                                          |
| **diffoscope / reproducible-builds.org**    | Deep recursive diff of archives, and the bit-for-bit reproducibility standard [E31][E32]                                                                                                       | Makes no judgment about whether a difference is malicious [E31]. Most npm and PyPI builds are not bit-for-bit reproducible **[H]**                                                                                                                       |
| **Socket**                                  | Behaviour and metadata alerts: install scripts, obfuscated files (detected with AI), unstable ownership [E23]                                                                                  | I found no feature that compares a package against its tagged repository [E23-search] **[H]**                                                                                                                                                            |
| **Snyk**                                    | Advisory database for malicious packages (CWE-506), compiled by its researchers [E24]                                                                                                          | Ignores provenance. Catches only what is already in its database [E24]                                                                                                                                                                                   |
| **Aikido Intel / Safe Chain**               | Scans every new version with static rules plus AI, then human review. Blocks installs of npm versions less than 24 hours old [E14]                                                             | Judges behaviour. Not documented to correlate with source **[H]**                                                                                                                                                                                        |
| **Veracode (Phylum)**                       | Firewall/proxy in front of npm and PyPI, plus a malicious-package database [E33]                                                                                                               | Same as above **[H]**                                                                                                                                                                                                                                    |
| **StepSecurity Artifact Monitor**           | Alerts when one of _your own_ npm releases has no matching approved CI run. Enterprise tier, early access [E22]                                                                                | Covers only your own packages. Compares where the package was built, not what is in it [E22]                                                                                                                                                             |
| **OpenSSF package-analysis**                | Runs packages in a sandbox and records files, network and commands [E34]                                                                                                                       | Does not compare against source [E34]                                                                                                                                                                                                                    |
| **deps.dev**                                | Shows the provenance repository and commit for npm packages [E35]                                                                                                                              | Only displays what provenance says [E35]                                                                                                                                                                                                                 |

**Gap UNMASK can fill in 12 hours [H, built on E26/E29/E31]:** produce a per-file, evidence-backed reconciliation between a package and the source commit named by its provenance. Classify each difference as **explained** (a build output we can reproduce or recognise), **expected** (packaging metadata) or **unexplained**, and give a risk reason for each. Two framings follow from the evidence:

- **"Provenance says _where_ it was built; UNMASK checks _what's inside_."** This is backed by npm's own disclaimer [E26] and by ChainDrop producing valid provenance for malicious builds [E19][E20].
- **"OSS Rebuild says yes or no; UNMASK says why."** UNMASK should also run where OSS Rebuild has no rebuild for a package.

## 4. What would make a judge say "wow" in 3 minutes

All of these are **[H]**, informed by §1–3.

1. **Show the clean case first.** Run a real, popular release from this week, minified `dist/` included, and get a green result. Every difference should be labelled "explained: generated by `tsc`/`esbuild`" or "rebuilt and matches". The judges' test set is mostly legitimate packages, so a quiet result on them is what earns the right to raise an alarm.
2. **Then a tampered copy.** Show one red row with file and line, the evidence and the risk: for example a new `postinstall` script, a dependency that never appears in the source (the axios pattern [E18]), or an injected line in `index.js` (the chalk pattern [E13]).
3. **Explain why provenance alone isn't enough.** Show a package with valid provenance that still contains unexplained content, linking the ChainDrop write-ups [E19][E20].
4. **Keep the model honest.** Gemma's explanation should cite file and line, and a programmatic check should verify each citation. Uncertain items should be labelled "unexplained", not "safe".
5. **Avoid a growing list of exceptions.** Explain differences by rebuilding or using build-tool rules (sourcemaps, `.d.ts` files, bundles), not by maintaining a per-package allowlist. The brief favours extensible approaches.
6. **Bonus:** show a "watch" feed of new releases, and a signal for keyv-style attacks where the source itself was compromised: provenance points to a commit that is unsigned, not on the default branch, or behind a tag that was deleted and recreated [E20].
